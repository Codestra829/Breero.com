## Executive conclusion

BREERO has a substantial FastAPI/PostgreSQL test and migration foundation, but the API is not complete as a marketplace contract and is not ready to be described as production-ready.

The correct next action is not a repository-wide “fix all” sweep. The repository has several long, stacked feature branches and overlapping contract initiatives. The safe approach is to merge or retire dependencies in order, then address the highest-impact defects as independently reviewable slices with exact-head validation.

## Source contract used for this audit

The supplied BREERO architecture defines:

- one FastAPI `/api/v1` platform serving public, client, provider and administrator surfaces;
- separate identity, catalog, geography, timezone, provider, scheduling, capacity, booking, matching, dispatch, trust, communications and platform domains;
- thin HTTP routers calling authorization and application/domain services;
- PostgreSQL/PostGIS as the authoritative source for booking, capacity, hold, assignment, authorization and lifecycle correctness;
- separate booking-intent and submitted-booking aggregates;
- dependency-ordered delivery rather than one broad feature branch;
- an endpoint-complete standard that includes schema, authentication, authorization, ownership/tenant scope, validation, transaction handling, error mapping, OpenAPI and tests.

This audit treats those requirements as target state. It does not silently label a documented target route as implemented on `main`.

## Audit method

The audit inspected:

- protected `main` and current open PR metadata;
- FastAPI construction, V1/V2 mounting and readiness logic;
- V1 router registration and capability conditions;
- checked-in API inventory and OpenAPI generation;
- backend pytest, migration, schema-drift and CI entry points;
- frontend unit, contract, build and browser-test configuration;
- the active stacked API program.

This was a read-only repository audit except for adding this documentation and `AGENTS.md` on a dedicated docs branch.

## Git-state risk

Green checks on a stacked head prove that head against its temporary parent. They do not prove:

- independent approval;
- correctness after each parent is squash/merge committed into `main`;
- migration compatibility of the final combined protected-main lineage;
- the final release candidate’s exact OpenAPI artifact;
- production readiness.

The required merge pattern is:

```text
review parent
→ merge parent
→ verify new main
→ retarget/synchronize child
→ rerun exact-head CI
→ fresh review
→ merge child
```

The compatibility transition needs a versioned/deprecation plan, not an unannounced rename.

# 4. Highest-impact concrete defects

## P0 — The implemented target API is not on protected `main`

**Evidence**

- `main` readiness is still tied to migration `017_provider_credentials`.
- PRs #68 and #85–#88 contain migrations `018` through `022` and the target identity/provider/booking/geography/provider-catalog APIs.
- Those PRs are unmerged and mostly stacked drafts.

**Impact**

The repository cannot honestly present the documented target API as a protected, integrated release candidate. Individual branch checks do not certify the final merge lineage.

**Required slice**

Merge and verify the dependency chain one PR at a time. Do not add more descendants until the parent review/merge queue is under control.

---

## P0 — Browser E2E does not certify the real FastAPI/PostgreSQL workflow

**Evidence**

`apps/web/playwright.config.ts` starts Next.js with:

```text
NEXT_PUBLIC_API_MODE=mock
NEXT_PUBLIC_E2E_ALLOW_MOCK=1
```

unless an external `E2E_BASE_URL` is supplied. The required frontend workflow does not set a real staging/API base URL; it invokes the default Playwright command.

**Impact**

Chromium, Firefox and WebKit success proves frontend behavior against mock contracts, not:

```text
Next.js → FastAPI → PostgreSQL/PostGIS → Redis/Celery
```

It cannot certify login/session cookies, CSRF, ownership, migrations, real validation, booking persistence, provider tenancy or dispatcher state.

**Required slice**

Create `ci/real-api-e2e-certification` after the API dependency chain is merged. Run isolated PostGIS/Redis/API/web with deterministic adapters and prove client, provider and admin journeys against real API state. Keep the existing mock suite as fast UI coverage.

---

## P0 — Runtime route registration makes OpenAPI environment-dependent

**Evidence**

`apps/api/app/api/v1/router.py` omits whole route families when feature settings are false. `apps/api/scripts/generate_openapi.py` imports `app.main` and serializes whichever routes are mounted in that process.

Affected families include address, payment, finance and paid-lead APIs.

**Impact**

The contract can vary according to generation environment. That creates drift among:

- runtime route availability;
- checked-in `openapi.json`;
- `docs/backend-api-inventory.md`;
- frontend contract checks;
- production configuration.

It is also unclear whether a disabled capability should mean “route absent” or “route present but fails closed.”

**Required slice**

Create `refactor/api-contract-determinism` and adopt one explicit policy:

1. register contract-stable routes and enforce capabilities inside the operation; or
2. generate separate, named contract profiles with deterministic environment inputs and no ambiguous canonical artifact.

Do not change this implicitly while adding features.

---

## P0 — Endpoint security/ownership policy is not enforced as a complete registry on `main`

**Evidence**

The OpenAPI generator validates operation-ID presence and uniqueness, but it does not require every method/path to declare:

```text
owner
audience
authentication
permission
tenant/legal-entity scope
record policy
capability
idempotency/version policy
PII classification
rate limit
emitted event
```

PR #62 proposes this control, but it is stacked on an older foundation and is not part of `main`.

**Impact**

New routes can be documented and tested without one machine-enforced policy record. Reviewers must reconstruct authorization and correctness from scattered files.

**Required slice**

Rebuild the intent of PR #62 on the final accepted API foundation after the current parent stack is resolved. Make the runtime registry and OpenAPI extension deterministic and fail closed.

## P1 — Canonical route namespace and current route namespace diverge

**Target contract**

```text
/api/v1/booking/*
/api/v1/client/*
/api/v1/provider/*
/api/v1/admin/*
/api/v1/messages/*
/api/v1/notifications/*
/api/v1/webhooks/*
```

**Protected-main contract**

```text
/api/v1/addresses/*
/api/v1/availability/*
/api/v1/bookings/*
/api/v1/customer/*
/api/v1/vendors/*
/api/v1/operations/*
/api/v1/integrations/*
```

**Impact**

Frontend clients, API docs and downstream integrations can implement different URL families for the same concept. A destructive rename would break existing clients, while indefinite duplication would increase maintenance and security review cost.

**Required slice**

Create a compatibility ADR and explicit migration matrix:

```text
legacy route
new route
shared service/command
response compatibility
deprecation header and date
consumer migration
removal gate
```

Introduce aliases only when both paths call the same authorization and domain service.

## P1 — Readiness is hard-coded to one migration revision

**Evidence**

`apps/api/app/main.py` declares:

```text
EXPECTED_SCHEMA_REVISION = "017_provider_credentials"
```

Every descendant migration must edit application code to update readiness.

**Impact**

This tightly couples a runtime health endpoint to a manually edited constant and makes stacked migration branches easy to misreport. It also complicates forward-compatible application/database deployment sequencing.

**Required slice**

Bind expected schema identity to a generated release manifest or build-time immutable value, and document compatible application/database revision ranges. Keep readiness fail closed.

---

## P1 — V1 and V2 error contracts are inconsistent

**Evidence**

V2 has a stable correlated `ApiError` path and explicit unexpected-error handling. V1 retains existing FastAPI and domain error shapes. The supplied target contract proposes a common `{data, meta, error}` envelope.

**Impact**

Frontend clients must parse multiple error shapes. A broad unversioned envelope rewrite would itself be breaking.

**Required slice**

Create a compatibility decision before changing response shapes:

- preserve V1 behavior;
- document current V1 variants;
- standardize required trace/rate/auth headers;
- introduce a new envelope only through a versioned or per-route migration with generated client evidence.

---

## P1 — The frontend contract check is a subset, not an API-completeness gate

**Evidence**

`scripts/check-frontend-openapi.mjs` checks a selected list of required public/customer routes and forbidden payment mutations. It does not certify every runtime endpoint, permission, schema, page-to-API mapping or target client/provider/admin route.

**Impact**

`pnpm contract:check` can pass while large parts of the target API are missing, undocumented or unused.

**Required slice**

Keep the current release-safety subset, but add generated client coverage and a page/API ownership matrix. Do not rename the subset check as complete API certification.

---

## P1 — Documentation describes capabilities that the mounted production contract may omit

**Evidence**

`docs/backend-api-inventory.md` states that the final source exposes 70 paths and 77 operations and marks payment/address families present. Runtime route registration is capability-dependent, and the checked-in inventory is not generated with its environment/profile identity.

The root README also describes a Stripe-to-confirmed-booking vertical slice while production release flags intentionally disable payments and automatic confirmation.

**Impact**

Operators and developers may mistake historical or capability-gated code for the active production contract.

**Required slice**

Generate the inventory from exact OpenAPI plus an explicit configuration profile and embed:

```text
source SHA
schema revision
contract profile
capability snapshot
path count
operation count
generation timestamp/tool version
```

Separate “implemented in source,” “mounted in this profile,” “enabled,” and “production certified.”

---

## P1 — No real-API skipped-test gate is visible in the final report

**Evidence**

Backend CI runs `pytest -q`, and there are PostgreSQL/PostGIS integration and concurrency suites. This audit did not find a root-level report that proves mandatory integration tests skipped equals zero for the exact release candidate.

**Impact**

A green test command may still conceal environment-dependent skips unless CI explicitly asserts the allowed skip policy.

**Required slice**

Add a CI assertion that parses the pytest result and fails when mandatory suites skip. Allow only named, documented environment-specific exclusions.

---

## P1 — CI and target runtime are not explicitly aligned

**Evidence**

The repository package metadata does not declare a Node engine. The frontend workflow uses Node 22. The supplied target architecture names Node 24 LTS.

**Impact**

There is no repository-enforced statement of which Node major is supported for local development, CI, image build and production.

**Required slice**

Use the existing `chore/node24-runtime-certification` workstream to choose and prove one runtime. Update package metadata, CI, Docker and documentation together only after frozen install, native dependency, Next.js build and browser tests pass.

---

## P2 — Repository test and API memory was not discoverable at the root

**Evidence**

No root `AGENTS.md` or equivalent API/test map existed. Backend pytest settings and frontend test configurations are valid but distributed across application directories.

**Impact**

Agents and contributors can incorrectly conclude that tests are absent, use the wrong working directory, or start changing code without understanding the branch stack.

**Resolution in this audit**

Added root `AGENTS.md` with implementation paths, test commands, Git preflight and completion rules.

---

## P2 — Backend dependency metadata contains duplicate Alembic declaration

`apps/api/pyproject.toml` lists the same Alembic dependency twice.

**Impact**

Low runtime risk, but it is a concrete dependency-hygiene defect and evidence that package metadata needs a small cleanup review.

**Required slice**

Remove the duplicate in a dependency-only branch and rerun frozen install, migration and image gates.

# 6. API completion definition

An API operation is complete only when all applicable fields are proven:

```text
method/path
request schema
response schema
stable operation ID
authentication
authorization permission
tenant/legal-entity scope
record ownership policy
capability policy
input and domain validation
transaction boundary
idempotency and request hash
optimistic/pessimistic concurrency
error mapping and required headers
rate limiting
PII classification
audit
transactional outbox/inbox
OpenAPI and generated client
unit test
PostgreSQL/PostGIS integration test
negative authorization test
concurrency/replay test
frontend contract/E2E where consumed
migration and rollback/forward-fix evidence
```

# 7. Audit limitations

This audit did not:

- run repository code locally;
- access production or staging hosts;
- run migrations against a live database;
- verify DNS/TLS/Caddy/Kong;
- merge any PR;
- activate a capability;
- assert that every test currently passes beyond recorded GitHub evidence.

A follow-on implementation slice must use exact-head CI and current review evidence rather than treating this document as test execution.
